## 2. 최소 상태 머신: 인지와 반응, 관계를 분리

```text
[인지하지 못함] --(정당한 source 열람)--> [누락 인지]
[누락 인지] --(권한·상태 적격)--> [확인 부탁 의도]
[확인 부탁 의도] --(상대 독립 수락)--> [근거 확인 중]
                         └--(바쁨/거절/단절)--> [보류/종료, 관계 감점 0]
[근거 확인 중] --(정정 게시+상대 인지)--> [기록 정정 인지]
               └--(이유 설명+유효 수용)--> [설명 수용 종료]
               └--(둘의 기준 불일치·유효 독립 행위·승인된 원인)--> [쟁점/갈등 별도 판정]
[정정/수용] --(별도의 감정 회복/거리 선택)--> [관계 후속 생활]
```

위 표는 처리 순서이고 `source`→ `OpenIssue`→ `Conflict`의 승격을 자동으로 뜻하지 않는다. 문제를 인지하거나 질문한다고 Conflict 250이 생기지 않는다. `DEV-25`의 갈등 250은 문서상 **정연우 정합 검수 전 비활성**이며, 이 문서가 활성화하지 않는다. 여기의 미지원 단계들은 새 상태 또는 기존 코드로 표현할 최소 원자 action을 결정하는 후보일 뿐이다.

## 3. 새 행동 후보 4종의 최소 계약 (디자인 전용)

| kind | 적격 입력 | 후보가 선택되면 | 결과 기록/비기록 | 금지·예외 |
|---|---|---|---|---|
| `credit_review` | actor가 자신에게 읽기 권한 있는 실제 `credit_record_id`·`help_source_id`를 알고 있고 최근 기록 확인 가능 | 정당한 해당 기록 read/recheck 요청(비동기라면 화면/상태 분리) | 사실 `read_committed`; 기존 관계 원장 새 긍정 source 없음 | source 없는 질문, 타인 비공개 기록 열람, 이미 같은 revision 반복 보상 불가 |
| `credit_state_standard` | C가 실제 기록+원인 문구/기준 snapshot을 소유, B가 설명 듣기 적격 | 자신의 적용 기준을 전달 | 증거 참조된 `standard_stated` action, C가 아는 범위만 말함 | 고집 카드만으로 규정을 새로 생성하거나 거짓 기여 부정 불가 |
| `credit_accept_explanation` | B가 그 설명과 근거를 실제 인지했고 의미상 수용 의사를 표현 | 원인별 `closed_explained` 또는 명시된 중립 종료 (정연우 검수 필요) | 독립 action id, 같은 원인에 idempotent; 자동 EVT·갈등 보상 0 | 설득된 척 자동 수락, 기억 삭제, 정정되지 않은 기록을 정정됐다고 말하기 금지 |
| `express_discomfort` | B가 알고 있는 구체 누락/약속 위반 등 독립 source가 있고 실제 영향이 서술 가능 | 상대가 듣기 전 불편 표현 시도 | 신체 행동/말풍선과 열린 문의(필요할 경우) 별개, 관계 8축 직접 변경0 | 미인지 항의, 고의 단정, 강제 싸움/250 자동 생성 금지 |

**개발 검증에 필요한 최소 필드(예시 이름, 스키마 확정 아님):** `action_id`, `intent_id`, `source_id`, `observer_id`, `target_id`, `knowledge_revision`, `record_revision`, `profile_rule_version`, `actor_room`, `eligible_snapshot`, `actual_response`, `completed_at_tick`, `dedupe_key`, `authority_order_id`. 원래 기록을 변경할 경우 단일 트랜잭션/검증 실패 rollback; 이벤트 source 참조와 보호대상 진행 중 증거는 checkpoint/압축에서 손실 금지.

## 4. 반응 독립성·진행 실패 QA 예시

1. A(다정한)가 B에게 도움을 제안해도 B가 휴식 중이면 수락하지 않는다. 대안은 A 자신의 작업·휴식이며 `positive_source=0`.
2. B(욱하는)가 C의 공로 기록을 못 봤으면 `credit_ask`는 부적격. 카드 점수 +12가 사실 인지를 대체하지 않는다.
3. B가 실제 누락을 알았으나 C가 바빠 확인을 거절하면 **갈등이 아니라 보류**, C가 나중에 가능하면 재접근 가능; 임의의 의무·기한 생성 금지.
4. C(고집 센)가 이전 기준을 설명해도 새 증거가 반박하면, `credit_review`와 `credit_accept_explanation` 중 적법한 후속 경로가 열려 있어야 한다.
5. B(독립적인)가 휴식 중이더라도 합의된 공동목표의 도움 자격이 있고 대상 동의와 여력이 충족되면 `assist` 후보 자체는 제거하지 않는다.
6. 정정은 됐지만 B가 정정자를 모르면 '기록 정정 인지'와 '정정자 인지'는 별도로 저장·공개한다. 갈등 해결과 실제 신뢰 회복은 자동 동치 아님.
7. 두 번 클릭/재접속/옛 record revision 재전송은 같은 action에 대해 1회 확정만 허용; source/action/quota/관계 효과 중복 0.
8. 2개 방에 분산되어 있으면 접근/목격 후보를 무효로 하고, 다른 방에서도 전역 Day 효과 상한은 우회 불가.

## 5. 우선순위·요구 소요 재산정

**최소 게이트 1:** 기존 후보 6종에 카드 보정 적용 + 선택/저장·기존폰 수정 + PERS-C01/C05/C06/C08/C09 검증. `credit_ask` 호출 가능하면 근거 있는 빠른 확인 연결.

**후속 게이트 2:** 현재 최신 코드에서 확인/기준 설명/설명 수용/불편 표현이 없으면 위 4종을 최소 원자 action으로 개발 검토. 단순 말풍선 문자열 교체로 완료 처리 금지. 관계 사건의 의미는 정연우, 콘텐츠 대사는 김플레이, 제품 범위는 김PO의 결정을 거친다.

**개발자 요청:** 현재 코드 enum/trace, 독립 수락 모듈, 기존 record source·목격·정정 action, 저장 버전, 읽기·정정 중단 처리, 실제 도달성·예상 작업량을 김PO 경유로 회신. 새로운 액션을 사용하지 않고 기존 action으로 구현할 수 있으면 별도 신규 kind를 강제하지 않는다.
