## 2. 유료 도메인 표시 결정

**이번 버전에는 Supabase 사용자 지정 도메인 구매/변경을 하지 않는다.** 현재 프로젝트 도메인으로 인증 시험을 이어가고 앱 안에서 외부 인증 화면 이동을 분명히 안내한다. 주소표시 꾸미기 때문에 로그인/두방 제작을 지연하지 않는다.

현재 [Supabase 공식 문서](https://supabase.com/docs/guides/platform/custom-domains)는 유료플랜의 유료애드온 및 서브도메인을 설명한다. 향후 도입한다면 `auth.neinom.com` 등 인증용 서브도메인이 후보이며 웹사이트 루트 `neinom.com`을 바로 같은용도로 바꾸는 것으로 이해하지 않는다. 결제·DNS·OAuth callback/CSP·세션/메일링크 영향을 포함한 실제견적을 새 결정으로 올린다. 이번 결정을 기술적으로 불가능하다는 뜻으로 표현하지 않는다.

## 3. Google 앱 게시 시점

현재 테스트 상태를 유지한다. **아래 공개 전 시험과 설정 확인을 마친 뒤 실제 공개일에 맞춰 Production 게시**한다. 두방·카드·친구공존 전체완료를 게시조건으로 늘리지 않는다.

공개 전 실제 시험:

1. AUTH03: 재설정 메일→새비밀번호→새비밀번호로그인, 만료/재사용·같은/다른브라우저·동일주소확인/재설정 혼동 방지.
2. AUTH07: 두기기가 같은 서버version에서 각기수정·저장→한쪽충돌, 원본/로컬백업·명시선택·별도저장.
3. AUTH10: 계정A 로그아웃→게스트/계정B→A자료 자동노출/잘못된B저장 없음.
4. AUTH12: 이메일확인계정→같은Google, Google먼저→비밀번호추가, 미확인주소선가입, 다른이메일 Google의 격리. 자동연결은 승인된 제공자정책과일치해야 함.
5. 세션만료·로그인취소/실패·오프라인/재진입은 mock과실기를구분해 검증한다. 확인되지 않은 경로는 제한을화면과납품목록에명시한다.

공개 설정은 실제Google Console의 앱표시명/지원정보·도메인소유·callback·사용scope·요구된verification 상태를확인한다. Production 전환과 브랜드검증완료는같은것이 아니다. 필요한 검증은 [Google 공식 공개 준비 문서](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification)를 대조한다. 콘솔을직접변경/게시했다는보고는이번에하지않는다.

## 4. 로그아웃·캐시 보완 요청

DEV26은 ‘서버자료·로컬월드그대로, 다른계정연결기록지움’으로 설명한다. PO-AUTH001은 계정캐시를 새게스트와분리하고 기기에개인사본을남기는것을명시선택으로 정했다.

서버에서불러온계정A월드가 로그아웃후일반게스트이름/폰화면에자동보이는지검사한다. 단순히서버연결키만지우는것은격리완료가아니다. 개인사본을남기려면범위를설명하고사용자가선택해야 한다. 비공개캐시/소유매핑과독립게스트저장을구분하며 계정B로실수업로드되지않게한다. 서버원본삭제와로그아웃은별개다. 최신코드의실제행동이이미이계약과맞다면증거로회신하고불필요한중복수정은하지않는다.

다른브라우저로메일링크를열때 PKCE 문맥부족으로완료못하는경로의재시도/원브라우저안내를실제시험한다. 사용자가가입·재설정을끝없이반복하지않게하며 비밀토큰을수동복사하도록요구하지않는다.

## 5. 두방·시작화면·디자인

두방저장형식3은 로컬구형저장/서버허용형식/다른기기클라이언트가함께영향받는다. SB0005에는허용형식검증·더새형식거절·이전형식보존/migration·충돌/복구·두방동일clock·같은관계scope를포함한다. 코드배포와서버허용범위변경의호환순서를제안하고반쪽migration을피한다.

PO-START001 스플래시/로그인/게스트/이어하기 요구는 별도 미완료 항목으로 유지한다. 현재 ‘더보기→계정’ 구현만으로새시작화면완료를선언하지않는다. 김디자인은큰칸판/계정두줄·실패/복구/세로가로·DPR 및 두방마스크를 검수한다. 신규자산은김도현이규격과기존원본을김PO에게요청한다.

국소분쟁/카드 추가안은 이미인계한정본을사용한다. 인증미완료를기다리며검수문서를반복생성하기보다두방개발과남은실기과제를병행한다.
