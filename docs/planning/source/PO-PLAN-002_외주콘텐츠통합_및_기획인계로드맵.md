# PO-PLAN-002 — 외주 콘텐츠 통합 및 김PO 기획·개발·디자인 인계 계획

- 작성: 김PO / 수신: 프로젝트 관계자 / 작성일: 2026-10-13 / v1.0
- 관련: PO-PLAN-001, PO-PROC-001, PO-14, PO-DEC-001, REQ-01
- 상태: 협업 확장 계획. 외주 과제 발송·외주 결과 수령·개발 완료를 의미하지 않는다.

## 1. 기존 계획과 역할

PO-PLAN-001의 제품 방향을 유지하고 콘텐츠 기획 과정을 확장합니다. 역할 MD는 외주 역량과 작업 형식의 참고 자료이며 본 총괄을 외주 페르소나로 바꾸는 지시가 아닙니다. 현재 A1 공간 구현과 REQ-01 관계 검수는 계속합니다. 외주 결과를 기다리기 위해 기존 작업을 중단하지 않습니다.

| 담당 | 책임 | 결과 수신 |
|---|---|---|
| 김PO | 비전·범위·채택·세부기획·우선순위·모든 인계·게이트 판정 | 각 담당 보고 취합 |
| 김플레이(외주) | 생활 콘텐츠·꾸미기·관찰/방문 경험·재미 가설 | 김PO만 |
| 김시스템(외주) | 콘텐츠 규칙화·밸런스·성장/경제 후보·예외/시험 명세 | 김PO만 |
| 정연우 | 관계 의미·인지/해석·8축·갈등/회복·AUTO 기대값 검수 | 김PO |
| 김도현 | 현재 소스 기준 개발 계획·구현·기술 판단·실행 증거 | 김PO |
| 김디자인 | 화면·원본 자산·공간/축소/가림·실제 화면 검수 | 김PO |

외주 두 명은 내부 개발·디자인 담당을 직접 관리하거나 지시하지 않습니다. 외주 결과의 모든 요청/충돌은 김PO가 통합합니다. 김시스템의 관계 수치 제안은 정연우 검수 후 김PO 결정, 김플레이의 UX 제안은 김디자인의 제작 검토 후 김PO 결정으로 연결합니다.

## 2. 외주 진행 순서

1. 김플레이에 OUT-PLAY-001을 전달하여 생활 콘텐츠 6개·추천2개·사용자 여정·후속 성장/방문 후보를 받습니다.
2. 김시스템에 OUT-SYS-001을 전달하여 Day/반복/다양성 검토를 먼저 받습니다. 콘텐츠 의존 작업은 PLAY-PROP-001 수령 뒤 김PO가 연결합니다.
3. 김PO가 기존 12×8·3가구로 가능한 안, 재미 근거, 새 기능 비용을 비교해 시제품 후보 최대 2개를 선정합니다. 이는 제안 수량이며 채택을 보장하지 않습니다.
4. 김시스템이 후보를 규칙 카드로 바꾸고 정연우가 관계 증거/변화/반례를 검수합니다. 충돌은 대안·사용자 영향·작업량으로 정리해 김PO가 결정합니다.
5. 김PO가 채택/보류/수정과 적용 단계를 문서로 확정하고 김도현/김디자인 인계본을 작성합니다.
6. 실제 시제품 결과를 본 뒤 콘텐츠 수나 시스템 복잡도를 늘릴지 판단합니다.

첫 외주 결과에서 장기 계획 전부를 확정하지 않습니다. 후속 과제는 구현 결과와 개발자가 다음으로 요청한 세부기획에 맞춰 하나씩 발행합니다.

## 3. 김PO가 순서대로 작성할 세부기획

아래 번호는 계획이며 실제 문서가 작성되기 전에는 완료로 인용하지 않습니다. 개발 의존성이 다르면 김도현 제안을 받아 순서를 조정합니다.

| 단계 | 김PO 기획 결과 | 김도현 전달 | 김디자인 전달 | 외주/자문 입력 |
|---|---|---|---|---|
| A1 공간 | PO-14(작성됨), 자산 인계 보완 | 배치/경로/저장/권한·12검사 | 분리 가구·유효/막힘/취소·표시 정합 | 기존 공간 경험 보완만 |
| A2 관계 서사 | PO-15 예정: STORY-A/B/C·가벼운 위임·Day/반복·사실/해석 | 조건/증거/상태/기여·AUTO 매핑 | 행동·기억·갈등 상태 문구/표시 | REQ-01 정연우, SYS 반복, PLAY 경험 |
| A2 콘텐츠 보완 | PO-16 예정: 채택 생활 콘텐츠 최대2개 | 데이터/반응/완료/중복/복구·fixture | 오브젝트/표시/모션·상태별 자산 | PLAY6개→SYS규칙→REL검수 |
| A3 로컬 체험 | PO-17 예정: 첫 사용·재방문·편집·관찰·실패 복구 | 통합 흐름·AUTO22/DQA14·실행 안내 | 온보딩/일지/빈/실패·세로/가로 | PLAY 여정 및 실제 관찰 |
| B-ACCOUNT | PO-18 예정: 식별·연결·소유·복구/삭제 | 상태/권한/중복/충돌·운영 변경안 | 연결/실패/복구안 | SYS 상태 제안·DEV 기술 판단 |
| B1 친구 공존 | PO-19 예정: 초대/동의/입퇴장/차단/단절 | 서버 권위/공개/동시성·두 사용자 검사 | 방문 관리·소유 구분·중립 피드백 | PLAY 방문 경험·SYS 규칙·REL 경계 |
| 후속 생활 성장 | PO-20 예정: 해금/수집/꾸미기 순환 | 채택 시 공급/소모/저장·악용 검사 | 성취·해금·수집 정보 | PLAY 경험·SYS 경제 비교 |
| C 소셜 맵 | PO-21 예정: 광장·목적 맵 | 맵별 참여/권한/저장/활동 규칙 | 공간·목적 안내·입퇴장 | 외주 후속 과제, 관계 검수 |

외주 결과가 기존 A2 요구보다 늦으면 현재 STORY 계약부터 구현하고 콘텐츠 추가는 별도 변경으로 인계합니다. 제안만으로 A1 가구 수·방 크기·전투·로맨스·경제를 늘리지 않습니다. 기획 작성 중 필요한 기술 정보는 김도현에게 확인하고 임의로 소스 구조를 지정하지 않습니다.

## 4. 개발용·디자인용 인계의 차이

같은 콘텐츠 ID와 문서 버전을 공유하되 목적에 맞춰 작성합니다.

- 개발용: 입력·선행 조건·권한·순서·상태·증거·데이터·예외·멱등성·저장/복구·공개 범위·기대/금지 출력·시험·기존 코드 영향. 아키텍처 선택은 개발자 기술 검토로 확정합니다.
- 디자인용: 화면 목적·정보 위계·사용자 조작·폰 행동 표시·성공/거절/중단/실패·문구·원본/슬롯·축소/가림·접근성·검수 장면. 픽셀/파일명/확장자는 개발자 요청과 디자인 원본 필요를 맞춘 뒤 확정합니다.
- 공통: 콘텐츠 원본 ID, 확정/제안/미결 구분, 적용 단계, 완료 판정, 변경 로그. 기획 대사와 실제 인지 데이터가 충돌하면 수정합니다.

개발자가 자산을 요청할 때 목적/표시크기/원본 해상도/파일명/확장자/투명/기준점/레이어/manifest/필요시점을 김PO에게 제시합니다. 김PO가 디자이너에게 규격과 제작물을 인계하고 개발자에게 수령 상태를 회신합니다.

## 5. 재미 검증과 채택 기준

새 콘텐츠는 수량보다 다음 질문으로 평가합니다.

1. 선택지를 누르지 않아도 생활이 이어지고 반응 차이가 보이는가?
2. 공간 변경·관찰·꾸미기가 다음에 해볼 일을 만드는가?
3. 같은 성격/다른 관계, 같은 관계/다른 성격의 차이를 이해할 수 있는가?
4. 반복 상한 뒤에도 생활이 이어지고 점수 농사가 핵심 동기가 되지 않는가?
5. 거절·거리두기·갈등 후 독립 생활도 자연스러운 결과인가?
6. 친구 없이도 재미가 있고 방문이 강제 보상 조건이 아닌가?
7. 현재 기술/자산으로 작은 시제품을 만들 수 있고 시험 가능한가?

실제 관찰 과제는 ‘가구 위치를 바꾸고 달라진 행동 설명하기’, ‘두 폰이 협력/거절한 공개 근거 찾기’, ‘정정과 회복을 구분하기’, ‘다음에 꾸미거나 관찰할 일 고르기’입니다. 소수 관찰을 전체 시장 검증으로 주장하지 않습니다. 지표·합격 수치는 테스트 대상/환경을 정한 뒤 제안합니다.

## 6. 문서 운영과 전달 패키지

기존 문서번호를 유지합니다. 외주 요청은 OUT-PLAY/OUT-SYS, 외주 제안은 PLAY-PROP/SYS-PROP, 김PO 채택은 PO-DEC, 통합 인계는 PO-HAND, 단계 기획은 요청된 PO-15 등의 번호로 진행합니다. 이미 등록된 번호와 충돌하면 발행 전 대조합니다. 향후 PO-15~21은 예약이며 현재 사용자 요청 내용을 앞서 결정한 것으로 취급하지 않습니다.

외주 공통 첨부는 PO-PLAN-001·PO-14·PO-DEC-001 및 본 문서입니다. 김플레이는 OUT-PLAY-001, 김시스템은 OUT-SYS-001을 각각 추가로 받습니다. 서로의 초안이 필요하면 김PO가 해당 버전을 인계합니다. DEV-19 원문 미수령 및 현재 구현 상태는 개발자 보고 수준임을 함께 전달합니다.

**김PO는 외주 아이디어를 그대로 개발 목록으로 넘기지 않고, 경험→규칙→관계 검수→작은 채택안→개발/디자인 인계→실제 체험 확인의 순서로 책임지고 통합합니다.**
