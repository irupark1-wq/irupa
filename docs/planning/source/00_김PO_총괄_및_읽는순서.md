## 2. 김PO의 핵심 경험 정의

한 문장 약속: **직접 만든 동그란 폰들이 함께 살며, 선택과 사건으로 자신들만의 복합 관계를 만들어가는 월드.**

핵심 행동: 얼굴 만들기 → 함께 생활·활동하기 → 갈등과 협력의 선택하기.

핵심 루프: 제작 → 만남 → 공동 목표 → 사건 → 선택 → 수치·기억 변화 → 달라진 행동 관찰 → 다음 만남.

초기 타깃은 캐릭터 창작·생활·관계 이야기 관찰을 좋아하는 사용자라는 가설이다. 대상 연령·플랫폼은 확정하지 않았다. 전투나 경제 기능은 현재 핵심 관계 경험에 필요한 범위로만 검토한다.

## 3. 사용자 확정 요구와 제안의 경계

- 확정: 원형 얼굴, 눈·입·머리카락·프레임 분리, 자기 폰·다른 사용자 폰의 관계, 개인 월드, 친구 초대, 광장, 목적별 맵, 8개 관계 게이지 각 1~1000, 혐관을 포함한 다양한 관계, 생활·사건형 월드 분위기.
- 제안: 게임명, 초기 플랫폼 후보, 2D 시점, 기본값·임계값·공식·콘텐츠 수량·정원, 대표 폰 직접 조작, 공방을 최초 목적 맵으로 선택.
- 미확정: 엔진·서버·인증·운영·연령·수익화·예산·일정, 프레임의 정확한 의미.
- 첨부 문서의 김시스템·김플레이 명칭은 참고 조직 구조다. 이번 실제 분담은 사용자가 지정한 김PO·김디자인·프로그래머·정연우로 구성한다. 존재하지 않는 별도 담당자가 승인했다고 기록하지 않는다.

## 4. 범위와 우선순위

| 우선순위 | 내용 | 근거 |
|---|---|---|
| Must A | 파츠 제작·저장, 개인 월드, 폰 3명, 사건·기억·방향성 8축, 관계 피드백, 공동 공방 | 관계 핵심 재미를 작은 규모로 검증 |
| Must B | 계정·소유권·영속 저장, 친구 방문, 광장, 사용자 간 공방, 동의·차단·신고·재접속 | 원본 사용자 요구를 실제 소셜 흐름에서 충족 |
| Should | 선택 표정, 접근성 옵션, 관련 사건을 따라가는 관계 상세 | 자유 그림과 이해 가능성 보강 |
| Could C | 여러 목적 맵, 사용자 파츠 공유, 집단 관계 | 핵심 검증 후 확장 |
| Won't A/B | 전투, 경매·유료 재화 거래, 음성·자유 채팅, 생성형 AI 대사, 자유 맵 제작 | 제작·운영 범위 제한 |

A는 단일 사용자 검증 시제품이다. B가 사용자 요청 전체를 연결하는 최초 소셜 알파다. A만 완성하고 사용자 요구 전체가 완료됐다고 말하지 않는다. 정원과 폰 수는 견적·실측으로 바꿀 수 있는 제안이며, 바꿀 때 공통계약과 양쪽 PRD를 함께 갱신한다.

## 5. 책임과 승인

| 항목 | 작성 책임 | 교차 검토 | 통합 결정 |
|---|---|---|---|
| 비전·범위·우선순위·검증 기준 | 김PO | 디자인·개발·정연우 | 김PO 제안, 사용자 확정 요구 우선 |
| 화면·캐릭터·모션·아트 규격 | 김디자인 | 프로그래머, 관계 표현은 정연우 | 김PO |
| 기술·데이터·동기화·예외·테스트 | 프로그래머 | 김디자인, 관계 규칙은 정연우 | 김PO 범위 판단·개발 기술 검토 |
| 관계 해석·사건·경계·다양성 | 정연우 | 김디자인·프로그래머 | 김PO |
| 비용·일정·플랫폼·출시 | 실제 제작팀 견적 및 사용자 | 전 담당 | 사용자 최종 결정 |

이번 문서 승인 상태는 ‘인계 가능한 제안안’이다. 구현 가능성·일정·플레이 재미가 검증됐다는 의미의 승인은 아니다.

## 6. 첫 공동 작업 묶음

| 작업 | 담당 | 연결 작업 | 검토 결과물 |
|---|---|---|---|
| WP-01 파츠 편집·저장 | 김디자인 + 프로그래머 | SCR-01, 외형 버전·동일 ID | 캔버스 규격·저장 상태·복구·미리보기 |
| WP-02 관계 카드·상세 | 양쪽 + 정연우 | SCR-04, 방향성·공개 정보 | 공개 데이터 계약·문구·양방향 자기 폰 사례 |
| WP-03 첫 공방 사건 | 양쪽 + 정연우 | SCR-06/07, 사건·갈등·동의 | 역할→사건→선택→결과의 완결 흐름 |
| WP-04 월드 방문 | 양쪽 | SCR-02/05/08, 권한·접속 | 입장·초대·거절·퇴장·연결 끊김 |

우선 WP-01~03을 설계·제작 검토하고 단계 A에서 체험한다. B의 데이터·권한 계약은 A 때 예약해 소셜 확장 시 ID와 저장 형식의 파괴적 변경을 줄인다.

## 7. 검증과 다음 게이트

1. 상세 기획 검토: 공통 정의·상태·예외·공개 정보·검증 기준을 두 담당자가 같은 의미로 이해하는지 확인.
2. 기술 시제품: 자유 그림 저장·표정 변환·사건 재전송·복구를 실제로 시험. 아직 실행하지 않았다.
3. 핵심 경험 시제품: 폰 3명의 도움·갈등·회복을 플레이 가능하게 연결.
4. 플레이테스트: 5~8명 제안. 첫 폰 제작, 변화 이유 설명, 복합 관계 설명을 관찰. 실제 결과를 기록한 뒤 기준과 범위를 조정.
5. B 통합 검토: 친구 방문·광장·공방·차단·재접속·저장 원자성 검증.

일정은 단계 순서만 정한다. 인원·엔진·플랫폼이 없는 상태에서 주 단위 납기나 비용을 확정하지 않는다.

## 8. 앞으로 이 대화에서 역할을 활용하는 방식

- 사용자가 역할을 부르면 그 역할의 관점과 담당 문서를 기준으로 답한다.
- 공통 규칙이 바뀌면 김PO가 영향 범위를 기록하고, 디자인·개발에 교차 검토를 요청하며 관계 변경은 정연우 자문을 거친다.
- 새로운 작업을 진행할 때 현재 파일과 최신 사용자 결정을 확인한다. 이번에 만든 문서를 기억이나 상시 실행 봇으로 오해하지 않도록 기록을 기준으로 유지한다.
- 구현·배포 요청이 들어오면 실제 작업 범위와 환경을 확인하고 해당 결과를 별도로 보고한다. 이번 요청의 산출물은 역할별 기획·협업 문서다.
