# 《동그란 사이》 디자인·개발 공통계약 및 협업보드

- 버전: 0.2 / 2026-10-12 / 상태: 작업 기준 제안안.
- 목적: 같은 기능을 서로 다른 의미로 제작하지 않도록 화면·데이터·상태·결정 연결.
- 원본 사용자 확정 요구 > 최신 사용자 결정 > 이 문서의 통합 결정 > 역할별 상세 제안 순으로 해석한다. 구현 중 새 충돌은 조용히 덮어쓰지 않고 아래 변경 절차로 처리한다.

## 1. 공통 용어

| 용어 | 의미 |
|---|---|
| 폰 | 영속 ID를 가진 게임 캐릭터. 외형 변경과 관계 정체성은 분리 |
| 소유자 | 폰을 생성·편집하고 사용 허용 범위를 정하는 사용자 |
| 대표 폰 | 현재 직접 조작하는 폰. 다른 폰으로 바꿔도 관계 유지 |
| 방향 관계 | A→B의 평가. B→A와 다른 레코드 |
| 기억 | 특정 폰이 인지한 사건과 해석. 비공개 정보일 수 있음 |
| 사건 | 참가자·원인·인지·효과를 추적하는 영속 기록 |
| 관계 태그 | 역할·감정·긴장·과거의 중첩 상태. 내부 판정과 공개 문구 구분 |
| 동의 | 사용자의 활동 허용/중대 전환 승인. 게임 속 호감이나 관심과 분리 |
| 파생 게이지 | 자원·역할·약속·갈등 항목에서 산출되는 의존·권력·의무·갈등 |

8축 키: affection 애정, trust 신뢰, respect 존중, dependence 의존, power 권력, reciprocity 호혜성, obligation 의무, conflict 갈등. 모두 정수 1~1000. 숫자들은 심리 검사값이 아닌 게임 규칙이다.

## 3. 관계 화면 공개 계약 (CT-REL-01)

1. 자기 소유 폰 두 명: 양방향 전환과 정확한 8축·허용된 기억을 제공한다.
2. 다른 사용자 폰: 자기 소유 폰을 from으로 한 평가만 정확한 값·사적 기억을 제공한다. 반대 방향 전환 버튼과 사적 응답 필드를 제공하지 않는다. 임의로 금지 방향을 조회하면 `visibility=restricted, scores=null`과 안전한 안내만 응답한다.
3. 상대의 마음을 짐작하게 하는 공개 반응은 실제 공개 행동·사건에서만 만든다. 내부 양방향 태그를 그대로 보내서 상대의 애정·원망을 유출하지 않는다.
4. 공동 활동·상호 승인 관계는 공개 범위가 정해진 사실 라벨로 보여줄 수 있다. 개인의 평가 문구와 구분한다.
5. 클라이언트에 비공개 필드를 전달하고 숨기는 방식은 금지한다. 서버 projection 단계에서 제외한다.
6. 값 1, 빈 기록, 접근 금지, 로딩 실패는 서로 다른 상태다. 접근 불가 값을 0/1로 대체하지 않는다.

최소 화면 응답의 논리 항목 제안(개발 DTO의 direction/visibility/labels 등과 아래 의미를 일대일 대응):

```text
fromPawnPublic, toPawnPublic, visibleDirection,
scores[8], ownAssessmentLabels[], sharedFacts[],
visibleMemories[], openIssues[], commitments[],
lastVisibleEffect, revision, allowedActions[]
```

각 항목의 필드형·조회 범위·오류는 개발자 PRD에서 상세화한다. 게이지와 별도로 `basis_status`를 포함하며 공동 활동이 없는 권력 500에는 ‘공동 결정 기록 없음’을 붙인다. 비공개 정보 때문에 서버 행동이 거부되면 사적 이유를 노출하지 않는 ‘지금은 이 행동을 진행할 수 없습니다’ 수준의 문구를 사용한다.

## 4. 외형 계약 (CT-CHAR-01)

- 기준 캔버스 제안: 파츠별 512×512 RGBA, 중심 피벗. 월드 캐릭터 최종 크기는 실측 전 가정.
- 레이어: 뒷머리 → 원형 베이스 → 눈 → 입 → 앞머리 → 프레임·장식.
- 위치·크기·회전·보이는 상태를 원본과 분리 저장. 디자인 도구 좌표와 엔진 좌표 변환은 한 곳에서 정의한다.
- 외형 확정은 새 appearance_version으로 생성하며 pawn_id는 유지한다.
- 표정이 없으면 기존 파츠 변환으로 대체. 자동 얼굴 인식이나 그림 의미 분석을 필수로 요구하지 않는다.
- 투명 배경·파츠 순서·피벗·파일명·미리보기는 양쪽 인계 체크리스트를 공유한다.
- 미확정 플랫폼 때문에 엔진 전용 파일 형식과 런타임 압축은 현 단계에서 고정하지 않는다.

## 5. 공통 상태 및 피드백 (CT-STATE-01)

| 영역 | 상태 | 화면·처리 |
|---|---|---|
| 저장 | draft/saving/saved/failed/conflict | 성공 전 기존 확정 버전 유지, 실패 초안 복구, 충돌 비교 |
| 동의 | pending/accepted/declined/expired/cancelled | 진행 전 승인 확인, 거절·만료 점수 벌점 없음 |
| 접속 | connected/reconnecting/disconnected | 재접속 표시, 위험 명령 잠금, 서버 스냅샷 복구 |
| 공방 | forming/ready/running/paused/completed/cancelled | 선택·중단 조건을 상태별 제공, 기술 중단 벌점 없음 |
| 사건 | proposed/awaiting_consent/applied/rejected/cancelled | 적용 성공 후 변화 표시, 미적용 상태에서 수치 확정 연출 없음 |
| 기억 | knowledge=known/unknown, reason=known/unknown, resolution=open/resolved | 서로 독립적인 3차원. 사건을 알지만 이유 미확인·미해결 상태가 동시에 가능 |

상태명은 여기의 논리 상태를 뜻한다. 개발 저장 상태 대응: draft=idle(변경 없음)/dirty(미저장 변경), saving=saving, saved=saved, failed=error, conflict=conflict. 코드의 enum 이름이 달라지면 대응표를 제공한다. 공방 재연결 유예 60초와 동의 만료 24시간은 제안값이다. 네트워크 유예와 승인 만료는 실제 서버 시간, 게임 내 약속은 해당 활동의 활성 시계 기준이다.

## 6. 변경 요청 양식

```text
CR-ID / 작성 역할 / 날짜 / 상태
배경과 해결할 문제:
연결 요구·화면·데이터·사건·테스트 ID:
현재 규칙 → 변경 제안:
사용자 확정 요구에 영향:
디자인 의견 / 개발 의견 / 관계 자문:
비용·일정·저장·권한·기존 콘텐츠 영향:
결정 역할 / 결정 / 이유:
수정할 파일 / 검증 방법 / 남은 문제:
```

진행: 요청 등록 → 상대 담당 직접 검토 → 관계 규칙이면 정연우 자문 → 김PO 통합 선택 → 양쪽 문서·공통계약 동시 반영 → 검증 근거 기록. 상태는 proposed/reviewing/adopted_for_draft/implemented/verified/deferred/rejected. 문서 반영은 implemented나 verified로 표시하지 않는다.

## 9. 인계·리뷰 완료 기준

- 양쪽은 같은 요구·화면·상태 ID를 참조한다.
- 각 화면에 로딩·빈 상태·오류·거절·취소·재시도·권한 차이를 표시한다.
- 개발은 디자인에 필드와 가능 행동을, 디자인은 개발에 피드백·자산·접근성 요구를 제공한다.
- 값·태그·대사는 원인 사건과 연결하며 비공개 정보가 새지 않는다.
- 첨부 문서 제안이나 가상 역할 합의를 사용자 확정 요구로 바꾸지 않는다.
- 구현 전 정책 미결 항목은 표시하고, 재현 가능한 테스트 사례가 함께 전달된다.
- 실제 리뷰 교환과 반영 결과는 아래 기록에 추가한다.

## 10. 실제 교차 검토 기록

초기 교환: 김PO가 김디자인·프로그래머에 공통 화면 ID와 방향별 공개 범위를 전달했다. 프로그래머에게 원본의 버전 포함 멱등성 키·클램프 후 정보 수정 위험 검토를 요청했고, 정연우에게 관계 해석·동의·파생 축 검토를 배정했다.

프로그래머 회신: 규칙 버전을 최초 효과 식별자에서 제거하고 원장·checkpoint replay로 정정하도록 상세화했다. 비공개 방향·파생 태그를 서버에서 필터하는 화면 계약, 시계·명령 충돌·영속 처리·DEV 인수 사례를 작성했다. 김PO는 이를 DEC-04/05에 반영했다.

정연우 자문: 감사≠의무, 사전 고지≠자동 존중 보상, 중대 갈등의 강도·복구 조건, 권력 500 근거없음, 내부 양방향 태그 노출 문제를 디자인·개발에 직접 전달했다. 프로그래머의 회신에서 해당 항목 반영을 확인했고, 김PO는 DEC-08~12에 기록했다. 문서 검토이며 실제 게임 검증은 수행하지 않았다.

최종 확인: 김PO가 01·02·03을 읽어 화면 ID·파츠 순서·정원 제안·관계 공개 범위·저장 상태를 대조했다. 정연우가 디자인 문서의 방향·중립축·권력 근거없음·비공개 태그·승인거절 연출·미확인 이유 표현 반영을 확인했다. 지식/이유/해결은 단일 enum이 아닌 독립 차원으로 공통계약을 수정했다. 최초 사용자 요구와 원본 v0.1은 그대로 보존했다.

김디자인 최종 회신: 개발 PRD와 공통계약을 직접 교차검토하고 명령 `command_id`(원본 `request_id` 별칭)와 승인 `consent_id` 구분, 금지 방향 조회 처리, 기억 독립 3차원, 자문 반영을 확인했다. 문서별 담당자 검토 완료이며 실제 화면 제작·엔진 연결·인수 테스트는 다음 작업이다.
