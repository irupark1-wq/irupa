## 3. PO-AUTH-001 로그인 — 구현안

### 3.1 방식

- 인증: **Supabase Auth**(이미 이 게임 전용 프로젝트 `yvsqivhdwzbshpapfcsy`). 비밀번호 저장·재설정·메일 확인·Google OIDC 검증을 Supabase 가 합니다. 게임은 비밀번호를 만지지 않습니다.
- 브라우저 라이브러리: 공식 `@supabase/supabase-js` 를 버전 고정해 레포 안(`prototype/vendor/`)에 둡니다. CSP 가 외부 스크립트를 막기 때문입니다. CSP `connect-src` 에 이 프로젝트 주소 한 개만 추가합니다.
- Google: "Google로 계속하기" → Google → Supabase → neinom.com 복귀(PKCE). 취소는 정상 취소로 처리합니다.
- 이메일: **이메일+비밀번호**(가입 → 확인 메일 → 로그인, 비밀번호 재설정 메일). Supabase 가 그대로 지원하므로 방식 변경 제안은 없습니다.
- 게스트: 지금처럼 이 기기 저장(`game1-local-a-v1`)만. 서버 익명 계정은 쓰지 않습니다(SB-0003 7번에서 끔).

### 3.2 계정 저장 구조 (SB-0004 로 드릴 SQL)

지금 서버 표(`game1_worlds`)는 **계정당 월드 1개**라서 PO-AUTH-001 의 "로컬 월드를 별도 월드로 저장"을 못 합니다. 새 표를 추가합니다(기존 표는 그대로 두고 쓰지 않음).

| 항목 | 설계 |
|---|---|
| 표 | `public.game1_account_worlds`: `world_id`(uuid), `user_id`(auth 주체), `title`, `import_key`, `version`(서버가 올림), `world`(jsonb), 시각 |
| 소유 | RLS 로 `auth.uid() = user_id` 만. 이메일·표시 이름은 소유 키로 쓰지 않음 |
| 계정당 월드 수 | 최대 3개(트리거) |
| 가져오기 멱등 | `unique(user_id, import_key)`. `import_key` = 로컬 월드 id + 저장 fingerprint. 같은 업로드를 다시 보내면 같은 월드를 돌려주고 복제 0 |
| 저장 | `game1_save_account_world(world_id, world, expected_version)`: 버전 불일치면 `save.version_conflict`(마지막 요청이 조용히 이기지 않음) |
| 검증 | 형식(`save_format`)·크기·폰 3명 상한 서버 확인. 지원 안 하는 형식은 거절, 원본 유지 |
| 불러오기 | 다른 기기에서 목록 → 선택 → **정지 상태로 복구**, 오프라인 생활 소급 없음 |
| 기기 캐시 | 게스트 저장과 계정 저장을 다른 키로 분리. 로그아웃 시 계정 사본은 지움(명시 선택하면 남김). 계정 A 의 월드가 B 화면에 나오지 않음 |

### 3.3 화면 흐름

1. 더보기 → "계정" 화면: 지금 상태 두 줄(**로그인 상태** / **월드 저장 위치**)을 따로 표시합니다.
2. 로그인 중에는 생활을 멈추고 편집 초안을 보존합니다.
3. 로그인 성공 → "로그인했어요"만 표시합니다. 월드 저장 성공으로 표시하지 않습니다.
4. 로컬 월드가 있으면 "이 계정에 현재 월드 저장" 확인 화면(폰 수·마지막 저장·대상 계정)을 띄웁니다. 먼저 로컬 백업을 남기고, 서버 성공 + 소유 확인 뒤에만 "계정에 저장됐어요"를 표시합니다.
5. 계정에 이미 월드가 있으면 자동으로 덮어쓰지 않고 "계정 월드 불러오기 / 이 월드를 새 월드로 저장"을 고르게 합니다.
6. 실패·충돌·세션 만료는 생활 정지 + 로컬 사본 유지 + 다시 시도입니다. 실패 응답은 계정 존재 여부를 드러내지 않는 공통 문구를 씁니다.

### 3.4 Google·이메일 같은 사람 연결 — **김PO 결정 필요**

Supabase 는 **이미 확인된 같은 이메일**로 Google 로그인을 하면 그 계정에 Google 수단을 자동 연결합니다(끄는 설정 없음). 확인 안 된 이메일 계정에는 연결하지 않습니다(남의 주소로 미리 가입해 가로채는 공격 방지).

- 이것은 "두 계정을 나중에 합치는 것"이 아닙니다. 같은 이메일을 두 방식으로 모두 증명한 한 계정입니다. PO-AUTH-001 §5 의 "인증 제공자의 검증된 연결 정책"으로 받아들이길 **권장**합니다.
- 다른 이메일의 Google 을 직접 연결하는 기능(manual linking)은 Supabase 에서 아직 beta 입니다. 이번 버전은 **`link_pending`**(미구현, 기존 방식으로 계속 로그인 안내)으로 두길 권장합니다.

### 3.5 비밀번호 정책

- 최소 10자, 영문 대소문자·숫자 포함, 시도 제한은 Supabase 기본값을 씁니다.
- **유출 비밀번호 차단(HaveIBeenPwned)은 Supabase Pro 요금제(유료)에서만** 됩니다. Free 면 꺼진 상태로 출시하는지 김PO 결정이 필요합니다. 길이·문자 규칙만으로 충분히 안전하다고 보고하지 않습니다.

| 이름 | 지금 방 표시명 "새 방" → "생활방"(id 유지) |
| 작업량 | 약 3일 + 김디자인 막힘 칸 검수 |

필요한 자산(김디자인, 제작 시작 때 REQ 로 요청): 아늑한 방 배경 세로·가로의 바닥 사각형 좌표 확인, 침대·책장 막힘 칸 초안 검수, 방 선택 UI 상태(현재 방·폰 수·빈 방). 옛 배경은 `prototype/assets/legacy-room/` 에 있습니다.

## 5. 국소 공로 분쟁(severity 250) — 정의 초안 (정연우 정합 검수용, 비활성)

PO-HAND-007 §2 에 따라 "같은 소유자 로컬 폰 사이 국소 공로기준 분쟁"을 정의합니다. 검수 전까지 코드에서 생성하지 않습니다.

### 5.1 실제 근거가 되는 "기준 해석의 차이"

랜덤으로 불일치를 만들지 않습니다. 실제로 애매한 사실 하나를 씁니다: **도움의 크기**.
- 도움 원천에 `help_share`(작업 전체 시간 중 B 가 함께한 비율)를 기록합니다. 지금은 없으며 추가가 필요합니다.
- 공로 기준 `CREDIT-RULE-workbench-v1` 에 애매한 조항을 명시합니다: "짧게 거든 사람(25% 미만)도 이름을 적는가". 이 조항에만 해석이 갈립니다.
- 폰의 해석 입장은 성격에서 정해집니다(고정, 재현 가능). 공정성 민감도 high → 포함, low → 제외, medium → 상대 설명 수용. 성격에서 입장으로 가는 매핑 자체가 정연우 검수 대상입니다.

### 5.2 단계와 증거

| 단계 | 행동(새 action) | 행위자 | 조건 | 결과 |
|---|---|---|---|---|
| 1 | 확인 부탁(기존) | B→C | 누락 인지, 열린 확인사항 | 확인 수락 시 2단계 |
| 2 | `credit_standard_stated` | C | C 가 영수증을 확인했고 **B 의 도움을 사실로 인정**함. `help_share` < 25%, C 입장 = 제외 | "도운 건 맞아. 짧게 거든 건 기준상 안 적어." C 는 사실을 부정하지 않습니다(거짓말 분기 아님) |
| 2' | (기존 정정) | C | C 입장 = 포함, 또는 `help_share` ≥ 25% | 정정 → EVT-09 경로(갈등 없음) |
| 3 | `credit_standard_contested` | B | B 입장 = 포함 | "짧아도 같이 했으니 적어야 해." |
| 3' | `credit_explanation_accepted` | B | B 입장 = 수용 | 확인사항 `closed_explained`, 갈등 없음 |
| 4 | Conflict 생성 | 시스템 | 2와 3 이 모두 저장 확정 | `conflict_id = dispute-<record>`, topic `credit_attribution`, scope = 그 기록 하나, 방향 **B→C 만**, severity **250**, evidence = 도움 원천·기록·2·3 action id, impact = 그 기록 한 건의 이름 표시 |

### 5.3 지키는 것

- 시간 경과·같은 근거 재전송으로 250 → 450 이 되지 않습니다. 같은 기록에서 두 번 생기지 않습니다(conflict_id 고정).
- 다른 활성 갈등을 닫지 않습니다. 태그·친밀은 자동으로 붙지 않습니다. 새 감정 감점·확률을 추가하지 않습니다(Conflict 축 값만 250).
- C 바쁨·미회신·권한 없음·기술 단절·정정자 미인지·기준 없는 메모에서는 생기지 않습니다(DEV-24 반례 유지).
- A 귀책 없음, C→B 자동 복제 없음.

### 5.4 해결 조건 (`resolution_condition_ref = credit-standard:<record>`)

- 원인 = "그 기록에서 B 이름이 기준 해석 때문에 빠짐". 다음 중 하나면 해결입니다.
  1. C 가 이후 기록을 실제로 정정·게시하고 B 가 그것과 정정자를 인지합니다. 이것이 유일한 원인을 해소하므로 해결이며, **EVT-09 한 번만** 생깁니다(EVT-12 추가 없음, 같은 증거 이중 사용 금지).
  2. 두 폰이 조항 해석에 합의하는 별도 대화 action 이 있고, B 가 그 결과를 인지합니다. 감정 효과는 없습니다.
- 해결돼도 기억은 남습니다. B 의 거리두기는 가능합니다.
- 해결되지 않으면 `open` 으로 남습니다. 정정을 언제 다시 시도할지(쿨다운)는 검수 후 정합니다.

### 5.5 정연우·김시스템 검수 요청 항목

1. 25% 조항과 성격에서 입장으로 가는 매핑이 "실제 대립"의 근거로 충분한지.
2. 2단계 C 대사가 사실 인정을 분명히 하는지(기여 부정·거짓말과 구분).
3. 해결 조건 1·2 와 EVT-09 단일 보상 처리가 맞는지.
4. 반례 목록에 빠진 것이 있는지.

검수 통과 후 작업량은 약 1.5일입니다. 도달 빈도 실측(2000tick × seed 4)과 실제 말풍선 증거를 그때 제출합니다.

## 6. 대사 실제 키 매핑 (정연우 v1.4 §5-1, 검수표 §2 요청)

DLG-05~08 은 정연우님 검수표의 번호이고 코드 키가 아닙니다. 코드 키는 아래 5개입니다(`prototype/dialogue.js`, `dev-provisional-v1`).

| 코드 키 | 말하는 폰 | 말투별 대사 | 호출 조건(저장 확정된 일지 한 줄) | 시점 |
|---|---|---|---|---|
| `credit_ask` | B | 따뜻: "기록에 내 이름이 없네. 같이 확인해 줄래?" / "아까 작업 기록 말인데, 한 번만 봐 줄래?" · 보통: "기록에 내 이름이 없네. 확인해 줄래?" / "작업 기록, 한 번 확인해 줄 수 있어?" · 무뚝뚝: "…기록, 한 번 봐 줄래?" / "작업 기록 확인 좀." | 일지 `accepted` "기록을 확인해 달라고 부탁했어요" 또는 `declined` "기록 확인을 부탁했지만 지금은 어렵대요" | 확인 부탁 commit 뒤 |
| `credit_ask_accept` | C | "그래, 다시 볼게." / "응, 확인해 볼게." | 위 `accepted` 줄의 두 번째 차례 | 〃 (확인 수락일 뿐 정정 수락 아님) |

| `credit_fixed` | C | "기록은 고쳤어." / "작업 기록 다시 적어 뒀어." | 일지 `completed` "고친 기록을 전해 듣고 확인했어요"(C 가 B 에게 전달) | **정정 게시 commit + 전달 commit 뒤에만** |

- 혼자 기록판을 읽어 정정을 안 경우("고쳐진 작업 기록을 확인했어요")는 대화가 아니므로 대사가 없습니다.
- 저장 실패·되돌림이면 일지 줄 자체가 없어서 대사도 나오지 않습니다(SYS-07).
- 같은 일지 줄은 항상 같은 대사입니다. 새로고침으로 다시 연출하지 않습니다.
- 정연우 v1.4 예문과 다른 점: `credit_fixed` 가 "자료를 확인하고 이름을 반영했다"까지 말하지 않습니다. 김플레이 대사팩 또는 정연우 판정에 따라 바꿉니다.
