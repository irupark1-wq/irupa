## 2. 구현 구조 제안

한 저장소에서 시작하고 실제 재사용 경계만 분리한다. 다음 경로는 제안 구조이며 아직 생성된 코드가 아니다.

```text
src/domain/       관계·사건·시계·태그·활동 순수 규칙
src/contracts/    명령·DTO·런타임 입력 검증·스키마 버전
src/content/      버전별 사건 정의·문구 키·검증 fixture
src/editor/       그리기·파츠·변환·undo/redo·초안
src/world/        렌더러 어댑터·경로·행동 표현
src/ui/           SCR-01~08·상태·접근성
src/adapters/     A 로컬 저장/B 서버 통신·캐시·복구
supabase/        migration·game1_ Edge Functions
tests/           규칙/통합/권한/장애/브라우저 검증
docs/            계약·결정·진행·운영·검증 증거
```

도메인은 DOM/렌더러/HTTP/실시간 연결을 참조하지 않는다. UI는 서버가 허용한 결과와 행동을 표현한다. A의 로컬 어댑터는 개발 체험 전용이며 B의 권한/보상 판정에 재사용하지 않는다. 라이브러리는 착수 시 공식 문서와 호환성을 확인하고 정확한 버전과 lockfile을 고정한다.

## 4. 사건·관계 규칙의 구현 계약

### 4.1 ID·수치

UUID 등 영속 식별자는 경계에서 검증하고 이름/외형을 ID로 쓰지 않는다. `(from_pawn_id,to_pawn_id)` 유일성, from≠to, 8축 CHECK 1~1000을 DB와 도메인 모두에 적용한다. 만남에서 두 방향 생성은 한 트랜잭션이다. 기본 점수100/300/300/1/500/500/1/1은 제안 버전 데이터로 둔다.

`round_half_away_from_zero`는 양수/음수 동률 모두 0에서 멀어지는 반올림으로 구현하고 음수 -.5 fixture도 시험한다. 부동소수/직렬화 차이를 줄이도록 배수 정밀도와 연산 순서를 계약에 고정한다. 점수는 각 유효 기여 슬롯 이후 clamp한다.

### 4.2 인지·감정·구조

EventFact, observer의 KnowledgeRevision, 당시 Interpretation, EffectLedger, 현재 Projection을 구분한다. 모르는 사건은 해당 방향 감정과 기억을 만들지 않는다. 객관적 자원/역할 변화는 별도로 계산한다. 기억은 knowledge/reason/resolution의 독립 3차원이다.

애정/신뢰/존중/호혜성은 인지한 감정 기여로 계산한다. 의존은 수신 A→제공 B의 중요도×기여비중×대체곤란도, 권력은 유효 활동별 중요도 가중 결정지분, 의무는 수락한 활성 책임 최대 burden, 갈등은 주제·scope별 열린 항목 최대 severity를 사용한다. 집계식은 PRD 제안 버전으로 저장한다. 근거 없는 권력은500+no_active_basis, 감사만으로 책임을 생성하지 않는다.

### 4.3 중복·정보 정정

- command receipt 유일키는 actor_user_id+command_id. 입력을 canonical serialize해 hash하고 같은 key/다른 입력은 충돌로 거부한다.
- 최초 effect 유일키는 source_event_id+observer_pawn_id+relationship_id+effect_kind. rule_version은 키에 넣지 않는다.
- knowledge_revision은 단조 증가, 같은 정보는 추가 감정 효과를 만들지 않는다. 권위자가 진위를 검증한다.
- 원 기여를 revision으로 대체하고 원 슬롯 직전 checkpoint부터 당시 규칙으로 순서 replay한다. 그 이후 checkpoint는 무효화/재생성한다.
- 시작990→+30→-20=980; +30을+10으로 정정한 replay도980. 단순 current-20=960은 불합격. 하한·여러 후속 사건도 시험한다.
- replay는 관계 projection 재계산이며 보상/알림/행동을 다시 실행하지 않는다. 구조 변경은 명시 상태 전이로 처리한다.
- discovery_effect가 정의된 경우에만 별도 key로1회 적용한다. 과거 규칙을 바꾸는 작업은 migration_id/dry run/대상/복구 증거가 필요하다.

### 4.4 태그·콘텐츠

감정 태그 진입은 서로 다른 유효 사건2회, 동일 틱·재전송·정보 정정은 추가 횟수0. 명시 역할 수락/종료, 과거 사실, 차단/철회는 즉시 반영한다. 진입/해제 임계값 원본 상세가 미수령이므로 테스트 임시값은 fixture임을 표시한다. 최종 임계값을 임의 승인으로 만들지 않는다.

초기12사건은 제안 콘텐츠다. 각 정의에 사실/인지/해석/감정 기여/구조 전이/기억/갈등/동의/문구 key를 기록한다. 선물 반복배수1/.5/.2/0은 같은 발신·수신·종류·활성일 조건에 한정하고 부정 사건/약속 이행에 자동 적용하지 않는다. 지연 사전 고지는 조건부 해석이며 반복 존중 보상이 아니다. 사과만으로 중대 상처를 해결하지 않는다.

표는 논리 이름 후보이며 실제 테이블은 책임별로 통합/분리 후 migration으로 생성한다. 노출 조회에 필요한 최소 public.game1_ 객체와 내부 game1_private.game1_ 객체를 구분한다. private 스키마를 Data API 노출 목록에 추가하지 않는다. 모든 게임 테이블 RLS를 명시하고 서비스 역할을 포함해 필요한 권한만 GRANT한다. service_role은 RLS를 우회하므로 이를 쓰는 서버 경로는 별도 게임/소유권 검증이 필수다.

단일 명령의 관계/기억/갈등/약속/보상/receipt/outbox를 하나의 DB 트랜잭션으로 확정한다. 여러 관계는 ID 정렬 잠금, 정원/위치는 참가와 동시에 예약한다. expected_version 충돌은 초안 보존, 서버 내부 CAS 재시도는 같은 명령ID/seed를 유지한다. 차단/철회와 활동 명령은 동일 권위 순서로 처리한다. commit 이후 outbox 전달 전에 현재 공개 권한을 다시 검사한다. receipt도 과거에 저장한 사적 DTO를 무조건 반환하지 않고 현재 권한으로 재투영한다.

구현 후보는 인증 Edge Function→검증된 DB 트랜잭션 실행 경로다. DB 연결/서버 전용 함수 가운데 G5 실험으로 선택한다. SECURITY DEFINER가 필요하면 내부 스키마·고정 search_path·검증·최소 EXECUTE를 적용하고 일반 클라이언트 호출 경로를 열지 않는다.

## 6. 화면·API·복구 계약

요청: command_id, expected_version, payload. actor는 검증된 JWT에서 정하고 클라이언트 owner_id를 믿지 않는다. request_id는 명령 별칭이며 consent_id와 다르다. DTO는 runtime schema로 검증한다.

응답: command_id/status/entity_version/event_id/event_sequence/reason_key/retryable와 허용 데이터. status와 reason_key는 개발이 fixture로 제공하고 디자인 문구와 일대일 대응한다. validation/conflict/permission/rate_limit/unavailable 범주를 구분하되 상대 차단/사적 이유를 밝히지 않는다. 기술 실패 시 같은 명령ID로 확정 여부를 확인하고 사용자의 새 의도만 새ID를 만든다.

| 화면 | 계약/작업 | 필수 복구 |
| --- | --- | --- |
| SCR-01 | Get/SaveAppearance·원본/변환/버전 | 로컬 초안과 확정 구분, 충돌 재적용 |
| SCR-02 | Get/SaveLayout·EnterInstance·InviteFriend | lease, 유효 배치/마지막 확정본, 입장 실패 |
| SCR-03 | GetPawn·SetRepresentative | 소유자 전용/공개 분리, 삭제 안전 표시 |
| SCR-04 | GetRelationshipProjection | 방향/visibility/basis_status, 금지 방향은 restricted/scores=null |
| SCR-05 | ListNearby·ProposeActivity·Block/Report | 정원·중복 제안·차단 이후 접촉 닫기 |
| SCR-06 | GetActivity·SubmitAction·RespondConsent·Leave | 승인/역할/비용, 기술 중단과 자발 퇴장 구분 |
| SCR-07 | GetEventResult | commit 후 delta, 연출1회, 순번 공백 동기화 |
| SCR-08 | Get/UpdateSettings | 설정 버전/철회, 초안, 차단 목록 |

정상 관계 DTO는 허용한 방향만 포함한다. 다른 소유자의 반대 방향/양방향 추론 태그/사적 이유는 서버에서 제외한다. 임의 금지 조회는 관계 존재·차단 여부를 특정하지 않는 restricted 응답. 이 정책을 조회·preview·결과·푸시·알림·참가자 목록·분석·행동 추천 모두에 적용한다.

저장 idle/dirty/saving/saved/error/conflict, 동의 pending/accepted/declined/expired/cancelled, 활동 forming/ready/running/paused/completed/cancelled, 사건 proposed/awaiting_consent/applied/rejected/cancelled를 유지한다. 성공은 commit 확인 후만 표시한다. 기술 중단/거절/만료의 점수 벌점은0이다.

복구는 stream ID+sequence cursor와 snapshot revision을 함께 사용하고 범위 만료 시 snapshot을 가져온다. event_id+sequence로 연출 중복을 막는다. 차단/로그아웃/삭제/공개변경 시 화면과 사적 캐시를 제거한다. Realtime private channel도 권한을 검증하며 전달 계층을 게임 판정으로 믿지 않는다. [공식 권한 안내](https://supabase.com/docs/guides/realtime/authorization).

## 7. 외형·생활 계약

파츠 원본512×512 RGBA/정규화 좌표/중심 pivot/6슬롯 순서는 제안 CT-CHAR-01을 따른다. 회전 단위는 degree, 눈 모드는 pair 또는 separate를 manifest에 명시하는 개발 제안을 D-02에서 검토한다. 변환 허용 범위/장식 여유/프레임 의미는 최종 시안 전 확정하지 않는다. 디자인/엔진 좌표 변환은 단일 어댑터다.

편집 원본, transform, 합성 프리뷰, appearance_version, checksum을 보존한다. neutral 필수, 선택 표정 없으면 모션/기존 변환으로 대체하고 임의 그림 재생성은 하지 않는다. 최종 외부 이미지 업로드/파츠 공유는 A/B 제외하며 사용자 그림 PNG 저장과 혼동하지 않는다. raw SVG/스크립트 입력은 허용하지 않고 이미지 규격/크기/픽셀 수를 서버에서 검증한다.

욕구·성향·상황·최근 사건·관계·자리/자원에 따라 행동 후보를 결정한다. 예약 충돌/경로 막힘/탭 비활성화/일시정지 복귀를 시험한다. 약속은 원 clock_id/due_tick, 승인 만료는 UTC 서버 시간이다. 20분=1일/유예60초/동의24시간은 제안 config이며 실제 데이터로 확정하지 않는다.

## 8. 보안·품질·출시 게이트

- G0: 기존 시크릿 검사/CI 기반 유지, runtime 검증/타입/규칙 테스트 추가. 검사 명령은 실제 구성 후 실행 확인한다.
- G3: 로컬 플레이/편집/복원 E2E, 의미 있는 관계 반례, 접근성 상태 확인. 로컬 저장은 서버 확정 문구를 쓰지 않는다.
- G5: 익명/본인/타인/다른 게임 사용자·운영자 권한, JWT 오류/만료, 불법 owner_id/delta, 입력 hash 충돌, 동시 명령, 트랜잭션 실패주입을 시험한다.
- G6: 사용자별/IP별 요청 제한과 크기 제한, 허용 origin, 공방/초대/신고 악용, outbox 재전달·권한 변경 검증. 제한의 구체값은 부하/사용 흐름을 보고 config화한다.
- G7: MFA, 필수 CI/브랜치 설정, 의존성 취약점, Supabase advisors, 백업 복원, 로그 개인정보/시크릿, 삭제/신고 담당 확인. 치명 권한/데이터 손상 결함은 출시 차단한다.
- 성능: 실제 기준 기기/브라우저/정원 fixture를 기록하고 FPS/frame time/memory/loading, 확정 결과 p50/p95, 복구 시간, DB 호출·전송량을 측정한다. 광장16명30fps(목표60)/RTT100ms에서p95 500ms는 원본 제안이며 약속이 아니다.
